# CrossLayersAnalyzer — 跨层漏洞攻击链路分析器

在**原始固件二进制**上，判定硬件漏洞的触发条件**是否已被固件自身满足**。

> 这是本项目第五部分的核心交付物。它不是"找到漏洞"的工具，
> 而是"**判定给定固件是否已经构成硬件漏洞的触发条件**"的工具。

---

## 1. 要解决的问题

已有的硬件漏洞自动化利用工作（Coppelia / Microscope / ProcessorFuzz 等）回答的是：

> **能否构造一个程序**，让它触发某个硬件漏洞？

本项目回答的是另一个问题：

> **给定一份真实的、不可替换的固件**，它是否**已经**构成了该硬件漏洞的触发条件？
> 攻击者能否通过外部输入走到那段代码，并控制住触发所需的操作数？

这个区别不是措辞上的：

| | 已有工作（设计验证视角） | 本工作（部署系统威胁评估视角） |
|---|---|---|
| 输入 | 硬件漏洞描述 + ISA | 硬件漏洞描述 **+ 一份固定固件** |
| 自由度 | 可以任意构造指令序列 | **一条指令都不能改** |
| 产物 | PoC 程序 | "这份固件是否危险"的判定 + 证据 |
| 失败含义 | 我的搜索没找到 | **该漏洞在这份固件上不成立**（这才是可交付结论） |

甲方明确要求：**在原始硬件和固件上分析，不允许生成新的 ELF 去同时触发两侧漏洞。**
本工程的设计正是围绕这条约束展开的 —— 它是**特征**，不是限制。

## 2. 三个创新点

### 创新点 A（主）：固定程序约束下的可达性求解

把"触发条件是否被满足"形式化为一个**带固定程序约束的可满足性问题**：

```
存在外部输入 I，使得：
  ① 控制流条件成立：I 能使执行流到达触发点所在的块
  ② 数据流条件成立：I 能影响（taint reachable）触发指令的操作数
  ③ 硬件条件成立：操作数满足契约给出的约束（如除数 == 0）
```

其中 ① ② 的约束来自**固件本身**（不可修改），只有 ③ 来自硬件契约。
求解成功即给出"这份固件在此输入下会触发该硬件漏洞"的可复核证据。

关键设计：**可控性判定的分层**。简单地做污点分析会说"该指令可达即可利用"，
这是错的。本工程把可控性细分为：

| 判定 | 含义 | 证据性质 |
|---|---|---|
| `controlled` | 外部输入污点可达该操作数 | 强 |
| `constant` | 常量传播后操作数恒为定值 | 强（确定不可利用） |
| `not_controllable` | **无输入污点可达，但值静态未知**（如从常量地址 load） | 强（确定不可利用，但与 constant 不同） |
| `path_dependent` | 部分路径上可控、部分不可控 | 需按路径分别评估 |
| `unknown` | 信息不足或求解超时 | **弱 —— 不得并入负例** |

`constant` 与 `not_controllable` 的区别是本工程的一个细节要点：
前者是"我知道它是 5"，后者是"我不知道它是几，但我知道攻击者说了不算"。
两者在"是否可利用"上结论相同，在**证据性质**上完全不同 —— 混为一谈是
审稿人会抓的漏洞。

### 创新点 B：IR 层语义匹配（专利点）

硬件契约来自 RTL 侧（`div` 指令某操作数为 0），固件侧只有二进制。
在**指令级做字符串/操作码匹配**会被编译器的实现自由度击穿：

- 同一语义可能由不同指令实现（`li a0,0` vs `xor a0,a0,a0`）
- 同一指令可能承载不同语义（`addi` 出现在常量折叠链中）
- 常量可能被多级折叠、内联、重排

本工程在**统一 IR + 常量传播 + 输入无关性传播**三个层面做匹配，
而不是在汇编文本层面。匹配分四层过滤：操作类别 → 谓词满足 → 常量可行性
→ 可控性，每层都输出"距离满足还差什么谓词"（见创新点 C）。

### 创新点 C：约束进展度（替代代码覆盖率）

传统 fuzzing 用代码覆盖率当搜索反馈。在跨层场景里覆盖率是**弱相关**的：
到达了除法指令所在的块，不代表除数可控。

本工程用 **约束进展度（constraint progress）** 作为反馈信号：

```
progress = (已满足谓词数) / (契约可检查谓词总数)
```

每次分析都记录 `unsatisfied_predicates`（还差哪些谓词）。
这个信号可直接用于引导定向搜索、优先级排序和人工复核，
并且在报告中它是**可解释**的 —— 说得出"为什么还没到"。

## 3. 快速开始

### 安装

```bash
pip install -r requirements.txt
```

无需 WSL、编译器、商业 EDA 工具。纯 Python + 少量单文件 C 扩展，
**评审机上一键跑通** —— 这是为论文复现刻意做的取舍。

### 运行全量测试

```bash
python tests/run_tests.py
```

预期输出：

```
  [OK  ] 指令编码自检              1.5s
  [OK  ] IR 提升                   1.5s
  [OK  ] 证据图不变量              1.8s
  [OK  ] 端到端判定               10.9s
通过 4/4
```

### 对真实固件运行分析

```python
import sys
sys.path.insert(0, "src")        # 引擎包
sys.path.insert(0, ".")          # 契约包

from crosslayer import AnalysisConfig, run_analysis, generate_report
from contracts.div_zero import make_div_zero_contract

contract = make_div_zero_contract()
cfg = AnalysisConfig(
    target_id="modem_v2",
    route="B",
    input_regs=("a0", "a1"),      # 攻击者可通过哪些寄存器影响固件
)
run = run_analysis(
    "firmware.bin",
    contract,
    config=cfg,
    db_path="out/evidence.db",
    base_address=0x80000000,       # 裸二进制必须显式给基址
    arch="riscv32",
)
generate_report(run, contract, "out/report.md")
```

## 4. 当前验证状态

| 项目 | 结果 |
|---|---|
| 端到端样本 | **13 / 13 判定正确** |
| 精确率 Precision | **100.0%**（TP=4, FP=0） |
| 召回率 Recall | **100.0%**（TN=7, FN=0） |
| 指令编码器交叉验证 | **59 / 59**（对 capstone） |
| 证据图不变量检查 | **31 项全通过** |

样本集刻意包含对抗性用例，而不是"能跑就算过"：

| 样本 | 考的是什么 | 二分类标签 |
|---|---|---|
| `S1_positive_controlled` | 正例基线 | POS |
| `S2_negative_constant` | 操作数恒为常量 | NEG |
| `S3_negative_unreachable` | 死代码（不可达） | NEG |
| `S4_negative_absent` | 全程序无触发操作（阴性对照） | NEG |
| `S5_positive_multi` | 多触发点 + 纠正路径 | POS |
| `S6_neg_folded_chain` | **多级常量折叠链** | NEG |
| `S7_pos_partial_control` | 部分可控即触发（除数为 0） | POS |
| `S8_neg_load_derived` | **常量地址 load 派生**（值未知但不可控） | NEG |
| `S9_pos_branch_guarded` | 分支保护下仍可达 | POS |
| `S10_neg_dead_after_ret` | `ret` 之后死代码 | NEG |
| `S11_neg_taint_killed` | **污点被后续常量赋值清除** | NEG |
| `S12_pos_indirect_jump_table` | **跳转表间接跳转**（精确解析） | EXC |
| `S13_pos_indirect_pointer` | **完全动态函数指针**（兜底不误报不可达） | EXC |

`EXC` = 不计入二分类。这两个样本考查的是**可达性保真**
（"不得把可达误判为不可达"），而不是可利用性 ——
把它们计入 Precision/Recall 会制造出根本不存在的假阴性。
`Sample.binary_label` 字段显式标注这一点。

**零假阳性**是这里最重要的数字 —— 对安全工具而言，
把不可利用报成可利用（假阳性）比漏报更危险。

## 4b. 控制流可信度（间接跳转解析）

原始固件里的间接跳转（`jalr`/`jr`：函数指针、跳转表、`switch`）无法静态
确定目标。若不处理，目标块会被判"不可达"，从而**漏报真正的触发点**。

本工程采用**保守过近似**，宁可多连边也不漏边：

1. **跳转表识别** —— `lw t0, off(base)` + `lui base, hi` → 枚举表项地址
2. **已知函数入口** —— 静态可解析的 call/jump 目标
3. **孤岛入口兜底** —— 任何分支目标，以及终止指令之后的地址

代价与收益是明确的：过近似可能**多报**（假阳性方向），
但不会**漏报**（假阴性方向）。对安全工具这个交换是划算的。

每次分析都输出 `cfg_confidence`（high/medium/low），
并写入报告的「3b. 控制流可信度」一节 ——
**解析不出来的部分不允许被静默渲染成"不可达"。**

## 6. 设计纪律

这四条不是文档措辞，而是被 `tests/test_evidence.py` 机器检验的不变量：

1. **原始镜像不可修改**；一切结论引用原始地址，镜像以 sha256 固定身份。
2. **UNKNOWN 是一等公民** —— 信息不足时返回 UNKNOWN，绝不降级为"未发现"。
   `unknown` 在统计中单列，不并入负例。
3. **推理边与观测边严格分离** —— `edge_nature=inference` 的边证据级别必须 ≤ E1，
   `observation` 必须 ≥ E2 且携带仪器来源。**禁止把推断渲染成板上观测。**
4. **无法形式化的条件必须显式列出** —— `formalization_report()` 会报出
   未形式化谓词的比例，不假装已处理。

## 7. 证据级别约定

| 级别 | 含义 | 本工程当前状态 |
|---|---|---|
| E0 | 语义关联（契约 ↔ 代码位置） | ✅ 已实现 |
| E1 | 静态 / 约束满足分析 | ✅ **本工程主要结论层级** |
| E2 | 模型可重放（模拟器 / RTL） | ❌ 未进行 |
| E3 | 有漏洞 RTL 上验证 | ❌ 未进行 |
| E4 | 真实板卡验证 | ❌ 未进行 |

**因此本工程的报告只能支持这个结论**：

> "在这份固件的静态分析中，存在满足该触发契约可达性与可控性的候选。"

**不能**支持"该攻击在目标设备上成立"。这个边界必须在第一次向导师汇报时讲清楚，
否则后续会被当成作弊。

## 8. 已知局限

诚实列出，这些也是论文"Threats to Validity"一节的素材：

1. **仅支持 RISC-V**。ARM lifter 尚未实现。
2. **仅实现思路 B**（固件自身含触发硬件漏洞的代码段）。
   思路 A（固件漏洞触发硬件漏洞）与思路 C（硬件漏洞影响固件执行）尚未实现。
3. **间接跳转解析是过近似**：跳转表与函数指针采用保守兜底，
   可能把实际不可达的块判为可达（假阳性方向）。
   每次分析都会报告 `cfg_confidence`，低可信度时需人工复核。
4. **隐式流（implicit flow）未建模**：控制依赖导致的信息泄露不在分析范围内。
5. **契约依赖人工录入**：硬件触发契约目前需从上位报告手工构造。
   Microscope 等工具的自动反推尚未接入。
6. **无中断 / 并发建模**：时序窗口与中断交错未考虑。
7. **假阳性风险点**：`controlled` 判定基于污点可达，
   若外部输入实际在更早的位置被校验过，本工程不会发现 ——
   这是"可控"与"可利用"之间的真实差距。
   （注意这与第 3 条方向相反：第 3 条是可达性过近似，
   本条是可控性判定缺少"校验"这一环。）
8. **常量传播为块内 + 跨块 must/per-path**，不做法间（inter-procedural）
   精确传播。跨函数的数据流会被保守地判为 `unknown`。

## 9. 引用

本工程的方法论综合了以下工作（详见 `docs/01-跨层漏洞攻击链路-方法调研.md`）：

- **HardFails** (USENIX Sec '19) —— 保护间隙、漏洞 RTL 测试台、5 类缺陷 / 25 条安全属性
- **Microscope** (ASP-DAC '24) —— HW-SCM 结构因果模型 + 增量 SMT，从硬件漏洞反推指令模式
- **Coppelia** (MICRO '18) —— 面向硬件的后向符号执行与周期拼接
- **Granite** —— 软硬件泄露契约的模块化验证
- **rtl2µpath / SynthLC** (IEEE Computer '25) —— µpath 合成的可变性作为侧信道指标
- **If-Tracker** —— RTL 静态信息流验证与条件抽取
- **FuSS** (ACM TECS '25) —— 覆盖率导向的硬件 fuzzing，从已有轨迹出发做局部符号执行
- **ARMORY** (IEEE TIFS '21) —— 全故障注入仿真；对一种故障模型设防会加剧对另一种的脆弱
