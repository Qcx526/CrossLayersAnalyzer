## 问题 1：使用了哪些工具

### 1.1 运行时与依赖库（全部可 pip 安装，无系统级依赖）

| 库 | 实测版本 | 在本工程里干什么 | 如果去掉会怎样 |
|---|---|---|---|
| **Python** | 3.13.14 (AMD64) | 运行时 | — |

| **pyelftools** | 0.33 | 解析 ELF：段表、符号表、入口点、调试信息探测 | 只能吃裸二进制，符号/段信息全丢 |

| **PyYAML** | 6.0.3 | 配置解析（预留给契约/配置外置） | 仅影响便利性 |

安装：

```bash
pip install -r requirements.txt
```

### 1.2 刻意**没有**使用的工具，以及原因

这条比"用了什么"更重要 —— 它决定了论文能否被复现。

| 工具 | 为什么不用 |
|---|---|
| **WSL / Linux 子系统** | 本机安全策略直接拦截 `wsl.exe`（实测报 `PROGRAM BLOCKED BY SECURITY POLICY`） |
| **KLEE / angr** | 依赖 Linux 与 LLVM 工具链，装不进上述约束 |
| **Ghidra / IDA** | 商业或需 GUI 的大型工具，评审机部署成本高 |
| **商业 EDA（VCS / Verdi）** | 无授权；且本工程结论层级只到 E1，用不上 |
| **Microscope / Coppelia 本体** | 需 RTL 与 Linux 环境；当前作为**方法论来源**引用，而非运行时依赖 |

**这不是妥协，是取舍。** 纯 Python + 少量单文件 C 扩展意味着：评审拿到的是一台
干净机器上 `pip install` 就能跑通的实验，而不是"作者机器上能跑"的工程。
对一篇需要复现的论文，这个性质的价值高于用上更强大的工具。

工具链只是底座，**分析方法本身是自研的**：

## 问题 2：工程的输入输出是什么

### 2.1 输入

#### (a) 固件镜像 —— 两种格式

| 格式 | 入口函数 | 要求 |
|---|---|---|
| **ELF** | `load_elf()` | 自动识别（magic `\x7fELF`），从 `PT_LOAD` 程序头取段；无程序头时回退到 `SHF_EXECINSTR` 节 |
| **裸二进制 .bin** | `load_raw()` | **必须显式给 `base_address`** |

```python
load_firmware(path, base_address=None, arch="riscv32")
```

关于裸二进制那条"必须"：代码注释里写得很直白 ——
**"猜错地址会导致整个分析失效"**。裸二进制没有地址信息，
基址填错以后所有跳转目标、所有 load/store 地址全错，
但程序**不会报错**，只会安静地给出错误结论。所以这是硬性要求，不是建议。

自动识别的架构（`_detect_arch_from_elf`）覆盖：
RISC-V / ARM / AArch64 / x86 / x86-64 / PowerPC / SPARC / LoongArch。
**但 lifter 目前只实现了 RISC-V**，识别出 ARM 也只能加载、无法提升。

#### (b) 硬件触发契约 —— 来自上位（硬件侧）工作的交接面

契约是**代码**不是配置文件，位于 `contracts/`。当前实现了一份：`contracts/div_zero.py`。

为什么是代码而不是 YAML/JSON：契约里的谓词要引用 `OpClass` 这类枚举，
要能写 `divisor == 0` 这种操作数关系，还要能被 `formalization_report()`
统计形式化率。用配置文件会立刻退化成"注释掉的伪代码"。

契约结构（四段，实测输出）：

| 段 | 内容 | 实测值 |
|---|---|---|
| `pre` | 前置状态 | M 特权级；需 DIVU 存在；需 STORE **作为攻击链支撑条件** |
| `trigger` | **判别性**条件 | `ARITH_DIV` 存在 + `INPUT_CONTROLLABLE` |
| `deviation` | 偏差 | `wrong_register_result`，`constrained_by_hw=True`，期望 `0xFFFFFFFF` |
| `observe` | 观测方式 | 需要 `rtl_waveform`（RTL 波形） |

**`trigger` 里刻意不放 STORE。** 这是个容易踩的坑：如果把"结果写回内存"
也当成触发谓词，那么"有 store 但完全没有除法"的固件会被判成"触发事件存在"。
判别性条件（"这个硬件操作发生了"）与支撑条件（"结果能传播到安全资产"）
必须分开 —— 详见 `contracts/README.md`。

形式化完整性实测：**4/4 谓词可检查（100%）**，无未形式化条件。

#### (c) 分析配置 —— `AnalysisConfig`

```python
AnalysisConfig(
    target_id="modem_v2",        # 本次分析的对象标识（写进证据图）
    route="B",                   # 路线 A / B / C（对应导师三条思路）
    input_regs=("a0", "a1"),     # ★ 攻击者能通过哪些寄存器影响固件
    input_entries={},            # 显式指定外部输入入口地址
    solver_timeout_ms=10_000,    # SMT 超时
    max_candidates=50,           # 最多分析多少候选块
    min_progress=1.0,            # 判定为可行候选所需的最小约束进展度
    partial_threshold=0.34,      # 判为 path_dependent 的阈值
)
```

`input_regs` 是最关键的参数，它是**跨层分析的起点** ——
定义了"攻击者从哪进来"。若不填，流水线会自动把 `input_regs` 登记为
入口点（`input:a0` → `entry_point`），否则可达性只从程序入口出发，
就漏掉了"外部输入能到哪"这个跨层问题。

### 2.2 输出

#### (a) `AnalysisRun` —— 内存中的完整结果对象

```
run.run_id          运行标识（run_20260918_..._modem_v2）
run.image           FirmwareImage（含 sha256 身份）
run.program         程序对象，run.program.stats 是 CFG 统计
run.matches         契约匹配结果（含 progress / unsatisfied_predicates）
run.results         逐块判定结果（ReachabilityResult 列表）
run.graph_info      证据图写入统计
run.elapsed()       耗时
```

`run.program.stats` 的字段（写进报告的"固件程序摘要"表）：

```
blocks, edges, functions, unreachable_blocks,
indirect_jumps, indirect_resolved, indirect_unresolved, cfg_confidence
```

#### (b) 逐块判定 —— `ReachabilityResult`，7 种判定

这是本工程最核心的输出。不看单一分数，而是**分层判定**：

| Verdict | 含义 | 与"可利用"的关系 |
|---|---|---|
| `exploitable_candidate` | 可达 **且** 操作数可控，已进入 SMT 求解 | **强正例**：可给出一组触发输入 |
| `path_dependent` | 可达，但可控性随进入路径而变 | 需按路径分别评估，**不得笼统归入正或负** |
| `present_but_uncontrollable` | 片段存在可达，操作数恒为常量 | 确定不可利用（强证据） |
| `not_controllable` | 操作数不受外部输入影响，**但值静态未知** | 确定不可利用，**证据性质不同于上一条** |
| `present_but_unreachable` | 片段存在但不可达 | 不可利用（强度受 CFG 可信度限制） |
| `not_present` | 全程序无该操作 | 阴性对照 |
| `unknown` | 信息不足 / 求解超时 | **弱 —— 不得并入负例** |

`present_but_uncontrollable` 与 `not_controllable` 的区别是本工程的一个细节要点：
前者是"我知道它是 5"，后者是"我不知道它是几，但我知道攻击者说了不算"。
在"是否可利用"上结论相同，在**证据性质**上完全不同 —— 混为一谈是审稿人会抓的漏洞。

每个 `exploitable_candidate` 还带：

```
block_addr, key_addr, key_insn     触发点定位
path_from_entry, path_length       到达路径
entry_point                        从哪个入口进来的
taint_sources                      污点源
satisfiability, solver, timeout_ms 求解状态（sat/unsat/unknown）
input_constraints[]                ★ 求解出的具体输入值（var_name/width/model_value）
progress                           约束进展度（创新点 C）
notes                              人类可读的说明
```

`input_constraints` 是最有价值的输出：它给出**具体的模型值**，
即"把 a0 设成这个数就能触发"。这使结论可被独立复核。

#### (c) 落盘产物 —— 实测 `out/` 目录（33 个文件）

| 产物 | 内容 |
|---|---|
| `out/evidence.db` | **CLEG 证据图**（SQLite）。实测 36 节点 / 30 边，按类型分：`CodeLocation` 14、`FirmwareImage` 13、`Evidence` 6、`Capability` 1、`Deviation` 1、`TriggerContract` 1 |
| `out/reports/*.md` | 逐样本 Markdown 报告 **13 份**（`S1_*.md` … `S13_*.md`） |
| `out/summary.json` | 汇总指标（机器可读） |
| `out/run_all.log` | 端到端日志 |
| `out/samples/*.bin` | 13 个样本二进制（便于外部工具复核） |
| `out/encoder_selfcheck.log` | 编码器自检日志 |

`summary.json` 实测内容：

```json
{ "n_samples": 13, "n_ok": 13, "n_pass": 13, "accuracy": 1.0,
  "binary": { "tp": 4, "fp": 0, "tn": 7, "fn": 0,
              "n_excluded_from_binary": 2,
              "precision": 1.0, "recall": 1.0 },
  "contract": { "id": "HW-DIV-0001", "formalization": { "formalization_ratio": 1.0 } },
  "evidence_graph": { "ok": true, "nodes": 36, "edges": 30,
                      "inference_edges": 30, "observation_edges": 0,
                      "problems": [] } }
```

#### (d) Markdown 报告的章节结构（`generate_report()`）

```
1.  分析对象身份（镜像未被修改）        ← sha256 + 段表 + 无符号表/无调试信息警告
2.  硬件触发契约                        ← 形式化完整性 + 未形式化条件逐条列出
3.  固件程序摘要                        ← program.stats 全表
3b. 控制流可信度                        ← ★ 间接跳转解析情况 + cfg_confidence
4.  判定结果                            ← 7 类判定的计数
5+. 可行候选详情 / 路径相关详情 / 不可利用候选分析（负例）
末. 未决事项与证据边界 + 复现信息
```

两处设计纪律体现在报告里：

- **章节号是动态的**（代码里的 `sec` 计数器）。若固定编号，
  在"本样本没有可行候选"的报告里会出现 4 → 6 的跳号，让人误以为漏印了一节。
- **"3b. 控制流可信度"这一节只在存在间接跳转时出现**，
  且它的存在本身就是一条纪律：**解析不出来的部分，不允许被静默渲染成"不可达"。**

## 问题 3：样本从哪里找的，用的是什么

### 3.1 一句话回答

**不是"找"来的 —— 全部是自研合成的，共 13 个，
由 `tests/fixtures.py` 里的手写 RISC-V 编码器现场生成。**

### 3.2 为什么不用现成的真实固件

这是本工程最重要的方法论证成，也可能是最容易被质疑的一点。

真实固件（路由器固件、BootROM、开源 RTOS 镜像）**没有地面真值**。
没有人能在不解密、不跑 RTL 的情况下，权威地断言"这个固件第 N 个字节处
的除法指令，其除数在真实攻击下可被控"。

如果用真实固件做实验，就有两种结局：
要么无法给出 Precision/Recall（无真值），
要么真值由作者自己拍脑袋标注（**循环论证** —— 用自己的判断验证自己的工具）。

所以这里做了一个明确的取舍：

> **用合成样本换地面真值的确定性。**
> 承认它不能证明"在真实固件上有效"，
> 换取能严格证明"引擎逻辑正确"。

前者写成论文的 Threats to Validity，
后者写成实验数据。这个交换是清晰的、诚实的。

### 3.3 样本怎么合成的 —— 手写编码器

`tests/fixtures.py` 里手写了一个 RISC-V 32 位指令编码器，例如：

```python
def ADDI(rd, rs1, imm):  ...
def DIVU(rd, rs1, rs2):  ...
def LUI(rd, imm):        ...
def JALR(rd, rs1, imm):  ...
```

**关键点：不用汇编器、不用编译器。** 每条指令的机器码由 Python 位运算直接拼出来。
为什么这么麻烦？因为一旦用 `riscv-gcc` 生成，地面真值就依赖
"编译器确实按我预期的方式编码/优化了这段代码" —— 这个假设不成立且难验证。

位拼装则由 **capstone 反向交叉验证**（`tests/test_encoder.py`）：
把拼出来的机器码交给 capstone 反汇编，看它认不认。

```
指令编码器交叉验证：  59 / 59 通过
```

这条链条是：**编码器 → capstone 独立解码 → 一致**。
如果编码器写错了（比如 opcode 位放错），capstone 会直接报错或解成别的指令，
测试立刻红。这保证了**地面真值本身是可信的**，而不是"我相信我写对了"。

### 3.4 13 个样本各自考什么

样本刻意设计成**对抗性用例**，不是"能跑就算过"：

| 样本 | 考的是 | 二分类标签 | 期望判定 |
|---|---|---|---|
| `S1_positive_controlled` | 正例基线：可控 + 可达 | exploitable | `exploitable_candidate` |
| `S2_negative_constant` | 操作数恒为常量 | unexploitable | `present_but_uncontrollable` |
| `S3_negative_unreachable` | 死代码 | unexploitable | `present_but_unreachable` / `not_present` |
| `S4_negative_absent` | **全程序无除法**（阴性对照） | unexploitable | `not_present` |
| `S5_positive_multi` | 多触发点 + 纠正路径 | exploitable | `exploitable_candidate` + … |
| `S6_neg_folded_chain` | **多级常量折叠链** | unexploitable | `present_but_uncontrollable` |
| `S7_pos_partial_control` | 部分可控即触发（除数为 0） | exploitable | `exploitable_candidate` |
| `S8_neg_load_derived` | **常量地址 load 派生**（值未知但不可控） | unexploitable | `not_controllable` |
| `S9_pos_branch_guarded` | 分支保护下仍可达 | exploitable | `exploitable_candidate` |
| `S10_neg_dead_after_ret` | `ret` 之后的死代码 | unexploitable | `present_but_unreachable` |
| `S11_neg_taint_killed` | **污点被后续常量赋值清除** | unexploitable | `present_but_uncontrollable` |
| `S12_pos_indirect_jump_table` | **跳转表间接跳转**（可达性保真） | excluded | 只考"不得误判为不可达" |
| `S13_pos_indirect_pointer` | **完全动态函数指针**（兜底不误报） | excluded | 同上 |

分布实测：`exploitable=4  unexploitable=7  excluded=2`。

### 3.5 `excluded` 标签为什么存在（一个踩过的坑）

S12/S13 曾一度造成一个**根本不存在的假阴性**（`Recall=0.6667, FN=2`）。

原因：这两个样本的 `expected_verdicts` 列了多个可接受判定（因为间接跳转的
目标本就不唯一确定），于是它们被当成了"正样本"；但它们实际解析出的
判定不是 `exploitable_candidate`，就被计成了漏报。

修法：给 `Sample` 加 `binary_label` 字段，取值
`exploitable` / `unexploitable` / `excluded`，
**只有前两者参与 Precision/Recall**，并把 `n_excluded_from_binary` 写进输出。

这两个样本考的是**可达性保真**（"不得把可达误判为不可达"），
不是可利用性。把它们计入二分类指标，是用错误的尺子量对了的东西。

### 3.6 样本的规模

每个样本 3–10 条指令（实测 `n_instructions` 介于 3 到 10）。
短到**人可以对着反汇编手算出正确答案**。这是刻意的 ——
地面真值必须能被人工审阅，否则它就不是真值，只是另一个工具的输出。

### 3.7 换到真实固件后，样本这一环怎么变

样本集是**引擎自检**用的，不是论文的全部实验。真实固件到手后：

1. 引擎不变，直接喂 `.bin` + `base_address`；
2. 但没有真值，所以**报的是判定而非准确率**；
3. 交叉验证只能靠"人工抽取若干触发点，与报告对照"（E1 级）；
4. 要升级到 E2/E3/E4，必须在模拟器/RTL/板卡上重放 —— 这超出单人 + 一台电脑的范围。

## 问题 4：我该如何使用此工程

### 第 0 步：环境

```bash
cd F:\qcx\code\CrossLayersAnalyzer
pip install -r requirements.txt
```

本工程使用的解释器路径（已配好全部依赖）：

```
C:\Users\Administrator\.workbuddy\binaries\python\envs\default\Scripts\python.exe
```

> 注意：本机 PowerShell 管道会吃掉子进程的 UTF-8 stdout（读出来是乱码或空），
> 所以脚本一律**自己写日志文件**，再用编辑器打开。这不是缺陷，是环境适配。

### 第 1 步：先确认工程是活的（1 分钟）

```bash
python tests/run_tests.py
```

预期输出：

```
  [OK  ] 指令编码自检              1.5s
  [OK  ] IR 提升                   1.5s
  [OK  ] 证据图不变量              1.8s
```

退出码 0 = 全部通过。**这是论文复现脚本的第一条命令**，
也是任何改动后必跑的第一条命令。跑完看 `out/summary.json` 确认指标没退化。

### 第 2 步：看一个已生成的报告，理解输出长什么样

打开 `out/reports/S1_positive_controlled.md`（正例）
和 `out/reports/S8_neg_load_derived.md`（"值未知但不可控"的负例）。
这两个对照着看，能最快理解本工程的判定风格。

### 第 4 步：写一份新契约（换一个硬件漏洞）

复制 `contracts/div_zero.py` 改名，改这四处：

1. `pre` / `trigger` / `deviation` / `observe` 四段内容；
2. **`trigger` 里只放判别性谓词** —— "这个硬件操作发生了"。
   支撑条件（能写回内存、能被观测到）放 `pre`；
3. `provenance={"route": "A"/"B"/"C"}` 标注对应导师的哪条思路；
4. `source_ref` 写清上位工作的出处（哪个 RTL 报告 / 哪条安全属性）。

新契约上线前，**跑一遍 `formalization_report()`** ——
它会告诉你有哪些条件本系统检查不了。这些条件必须写进论文的
"未验证"清单，**不能假装已处理**。

### 第 5 步：读结果时的正确姿势

拿到报告后，按这个顺序读：

1. **先看「1. 分析对象身份」的 sha256** —— 确认分析的是你以为的那份固件。
2. **再看「2. 硬件触发契约」的形式化完整性** —— 若 < 100%，
   那些未形式化的条件就是结论的盲区。
3. **再看「3b. 控制流可信度」** —— 若 `cfg_confidence` 不是 `high`，
   所有"不可达"结论都要打折。
4. **然后才是「4. 判定结果」** —— 注意 `unknown` 是单列的，它**不是**负例。
5. **千万别把 `unknown` 和负例加在一起算比率** —— 那会伪造出一个漂亮的数字。

### 第 6 步：本工程**不能**用来做什么（一线之隔）

本工程的结论层级是 **E1（静态/约束满足）**：

```
E0 语义关联          ✅ 已完成
E1 静态/约束满足      ✅ 已完成  ← 本工程的主要结论层级
E2 模型可重放         ❌ 未进行
E3 有漏洞 RTL 验证    ❌ 未进行
E4 真实板卡验证       ❌ 未进行
```

所以它**只能**支持这个结论：

> "在这份固件的静态分析中，存在满足该触发契约可达性与可控性的候选。"

**不能**支持"该攻击在目标设备上成立"。这个边界必须在**第一次**向导师汇报时
就讲清楚 —— 否则后面会被当成作弊。

### 第 7 步：当前工程没做的部分（写给下一阶段的自己）

1. **仅支持 RISC-V**（架构识别到 ARM 了，lifter 没写）。
2. **只实现了导师思路 B**（固件自身含触发硬件漏洞的代码段）。
   思路 A（固件漏洞触发硬件漏洞）与 C（硬件漏洞影响固件执行）**尚未实现** ——
   契约里的 `route` 字段已经预留。
3. **契约靠人工录入**，Microscope 式的自动反推尚未接入。
4. **无中断/并发/微架构时序建模**。
5. **不做法间常量传播**（跨函数数据流会被保守判为 `unknown`）。
