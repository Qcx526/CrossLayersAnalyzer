# 如果我来做这个部分：单人可执行的路线与论文策略

> 前提假设（按你的实际情况）：**单人 + 一台电脑 + 目标是论文/专利**，甲方资料未到。
> 与 `01`/`02` 文档的关系：那两份是"项目该怎么做"；本文是"**我一个人现在怎么做**"。

---

## 1. 最重要的一个判断：主动砍掉一半

如果我是你，我做的**第一件事不是写代码，而是重新划定范围**。

项目书第五部分要求 5 类架构、跨层链端到端验证、100 条样本库、80% 命中率。这个规模是**一个团队 + 真实板卡**的活儿。单人一台电脑是**不可能**完成 L3/L4 级（RTL 实现级 / 板卡级）验证的——不是能力问题，是物理条件问题：你没板卡，没调试器，没示波器。

所以我的策略是：

> **不追求覆盖第五部分的全部指标，而是把其中一个技术点做深、做出可发表的成果，让它成为整个第五部分的技术内核。**

具体来说，我会选：

> ### **在原始固件二进制上，判断"硬件漏洞的触发条件"是否已被固件自身满足**
>
> 也就是导师第②条思路。用 Microscope 式的因果反推得到触发模式，用 Coppelia 式的符号执行在**原始固件**上求解可达性与操作数可控性，全程不修改固件。

**为什么是这个**：

| 理由 | 说明 |
|---|---|
| 你有全部必需要素 | Microscope 二进制版可下载；Coppelia 开源；HardFails 有 ground truth；公开固件镜像可获取 |
| 不需要板卡 | 全流程在主机侧完成，最后的"验证"可以用 RTL 仿真代替真实板卡 |
| 不需要 RTL 编写 | 用现成开源 RTL（OR1200 / mor1kx / PULPino / Rocket / CVA6） |
| 最贴合"不生成新 ELF"约束 | 因为找的就是原固件里已有的片段 |
| 论文创新点清晰 | 见 §5 |

**我会明确向导师说明**：L3/L4 级验证需要板卡，我会做到 L2（模型级可重放），并给出 L3/L4 的接口设计让别人接。这不是偷懒，是诚实的分工——Astra 方案 §9 的证据分级正好能支持这个论述。

## 2. 我会怎么排时间

按 6 个月算（论文周期），我会这样切：

### 第 1-2 周：把地基摸清楚，一行代码不写

这一步最关键，很多人跳过。我要在这两周内搞清楚四件事：

1. **读透 Microscope 论文 + 跑通它的二进制版**
   下载 `microscope.zip`（K-State 官网），在 Linux 环境（WSL 或虚拟机）跑起来，看它的输入输出到底长什么样。它输出的是 SMT-LIB 模型还是别的形式？"指令模式"具体是什么格式？——这决定我后面所有工作。

2. **读透 Coppelia 论文 + 看懂它的代码结构**
   `github.com/rzhang2285/Coppelia`，重点看 `cores/or1200` 和 `include` 里的约束文件。注意它依赖 **KLEE + Verilator 3.900**——这是个老版本，装起来会有坑，我要在第 2 周之前确认能跑通。

3. **确认 HardFails 测试床能不能拿到**
   论文说基于 RISC-V SoC 构造了 30 个 buggy RTL。我要确认是随论文发布、还是需要联系作者。**拿不到的话整个计划的 ground truth 就少了一半**，需要提前知道。

4. **选一个固件样本**
   我倾向选**有公开源码 + 能编译出原始二进制**的固件，比如 Zephyr / FreeRTOS 在某个 RISC-V 平台上的构建产物。**关键**：我需要**源码**来验证我的分析对不对（但最终分析对象是二进制，源码只用于验证）。

**第 2 周末的交付物**：一份 3 页的可行性备忘，说明三个工具都能跑、数据能拿到、我要解决的具体问题是什么。

### 第 3-6 周：复现基线，建立 ground truth

这一步是**论文的立足点**，不能省。

1. **在 Coppelia 的 31 个已知 bug 上跑通 Coppelia**，记录它生成的 exploit。
   - 目的：确认我有能力复现别人的结果。这是审稿人一定会问的。
   - 这一步会踩很多坑（KLEE 版本、Verilator 版本），但踩完就有底气了。

2. **把 Coppelia 生成的 exploit 反汇编，人工理解"它到底让处理器做了什么"**
   - 这一步是**关键洞察的来源**。我会发现：Coppelia 生成的是一个**独立的测试程序**，不是固件。它从 reset 开始跑，把处理器带到违规状态。
   - **这就是差距**：Coppelia 回答"能不能触发"，我要回答"**这份固件里能不能触发**"。这是两个不同的问题。

3. **对照实验设计**：对每个 bug，我把 Coppelia 的 exploit 提取成"触发语义描述"（需要什么指令、什么操作数关系、什么前置状态），然后**在原始固件里搜这个语义**。
   - 有些 bug 会立刻找到（固件中确实存在这样的片段）
   - 有些明显的负例（固件根本没有这类指令）
   - **正例和负例都有**，这就是一个好的实验设计

**第 6 周末的交付物**：一个能跑的脚本，输入"硬件漏洞描述"，输出"原固件中匹配的片段 + 是否可达"。跑在 31 个 bug 上，有初步的 Precision/Recall。

### 第 7-14 周：做出我的方法

到这一步我才开始"创新"。我要在 Coppelia 的路线上做三个改进：

**改进 1：从"生成新程序"转为"在固定程序上求解"**

这是核心的技术转变。

- Coppelia：符号执行从 **reset 状态**开始，求解"输入序列 → 违规状态"
- 我：固件已经在跑，符号执行从 **固件实际到达的状态**出发，求解"**什么外部输入 → 固件执行到某个已有的指令片段 → 该片段满足触发条件**"

技术上这是一个**受约束的符号执行问题**：搜索空间被固件的 CFG 限定了，而不是全状态空间。这反而**更容易**——因为固件已经替我们做了大部分决策。

我要处理的关键难点：
- **怎样从固件实际状态开始符号执行**（而不是从 reset）——涉及状态快照与状态导入
- **怎样把外部输入建模为符号变量**（而不是把寄存器全符号化）
- **怎样处理固件中的循环和中断**（不能用无限展开）

**改进 2：用 HW-SCM 反推的"指令模式"作为搜索靶标，而不是自己写安全断言**

Coppelia 需要人工提供"安全关键断言"（security-critical invariants）。我要把它自动化：
- 用 Microscope 的 HW-SCM 从硬件侧反推出触发模式
- 把它翻译成符号执行的目标谓词
- 这样就从"人工写断言"变成"从硬件漏洞自动导出靶标"

**改进 3：约束进展度作为搜索反馈**

符号执行在固件上会路径爆炸。我要的反馈信号不是"覆盖率"，而是"距离满足触发谓词还差哪个约束"。这个信号可以让搜索定向。

**第 14 周末的交付物**：论文的 core method + 实验数据。

### 第 15-24 周：实验、消融、写作

1. **主实验**：在 N 个（硬件漏洞, 固件）组合上跑我的方法，报告 Precision/Recall / 真链检出数
2. **消融**：
   - 去掉 HW-SCM 反推（改用人工断言）→ 看自动化带来的收益
   - 去掉约束进展度反馈（改用普通覆盖率）→ 看搜索效率的差异
   - 去掉可达性验证（只做模式匹配）→ 看误报增加多少
3. **对比基线**：
   - 只做指令模式匹配（无语义验证）
   - 只做符号执行（无 HW-SCM 靶标）
   - Coppelia 原版（作为"生成新程序"的上界参照）
4. **负例分析**：为什么某些 bug 在原固件中不可达？分类（代码不存在 / 不可达 / 操作数不可控 / 权限不足）
5. **写作**

### 第 25-26 周：缓冲

一定会超期。留两周。

## 3. 我会用什么技术栈（具体到命令）

**环境**：WSL2 + Ubuntu 22.04（因为 Microscope 二进制版要求 Linux，KLEE 和 Verilator 也都在 Linux 上更顺）

| 环节 | 工具 | 具体做什么 |
|---|---|---|
| 硬件侧反推 | **Microscope 二进制版** | 输入 RTL + 安全性质 → 输出指令模式 |
| RTL 仿真 | **Verilator 3.900**（Coppelia 要求）或更新的 Verilator | 把 RTL 编译成 C++ 做符号执行 |
| 符号执行 | **KLEE**（Coppelia 依赖）或 **angr**（更现代） | 在固件上求解可达性与操作数约束 |
| 固件反汇编 / IR | **Ghidra Headless + P-code** | 统一 IR，支撑多架构匹配 |
| 约束求解 | **Z3** | HW-SCM 求解 + 固件约束求解 |
| 固件样本 | Zephyr / FreeRTOS 的 RISC-V 构建产物 | 原始固件二进制 |
| 硬件样本 | OR1200 / mor1kx / PULPino（Coppelia 自带） + HardFails testbed | ground truth |
| 结果存储 | **SQLite + JSON**（按 `02` 文档的 CLEG schema） | 证据图 |

**一个技术选型上的犹豫，我会这样解决**：

Coppelia 用 KLEE（老，依赖 LLVM 3.4，装起来痛苦），而 angr 更现代、Python 生态好。我的选择是：

> **先用 Coppelia + KLEE 复现基线（第 3-6 周），然后评估是否迁移到 angr 做我的方法（第 7 周起）。**

理由：复现基线必须用原工具才有说服力；做自己的方法时用 angr 效率更高。如果 KLEE 装不起来超过一周，我会直接跳到 angr，并在论文中说明"我们在 angr 上重新实现了 Coppelia 的后向符号执行思想作为基线"。

## 4. 我会怎样把"不生成新 ELF"这个约束变成论文优势

这是你导师最看重的约束，我会把它反过来当成**创新点**来写：

**别人的做法**（Coppelia）：给处理器设计 + 安全性质，生成一个**新的测试程序**来触发漏洞。
→ 问题：这个程序在真实系统里跑不起来，因为它不是设备运行的固件。

**我的做法**：给硬件漏洞 + **一份真实的、不可替换的固件**，判断该固件是否已经/能够触发这个漏洞。
→ 优势：结论直接对应真实设备的真实威胁。

**这个对比在论文里会是这样一句话**：

> 现有硬件漏洞利用生成工作（Coppelia, MICRO'18；Microscope, ASP-DAC'24）回答的是"**能否**构造一个程序触发该漏洞"；本文回答的是"**给定的真实固件**是否已构成该漏洞的触发条件"。前者是设计验证问题，后者是部署系统的威胁评估问题。

**这个表述会打动审稿人**，因为它把一个"约束"（不能改固件）重新定义成了一个"新问题"。

## 5. 论文创新点我会怎么写（三选一或组合）

### 创新点 A（我认为最强的）：固定程序约束下的硬件漏洞可达性求解

**问题**：硬件漏洞的触发条件已知，但搜索空间受"必须由这份固件执行"约束。
**贡献**：一个受固件 CFG 约束的符号执行方法，从固件可达状态出发求解触发路径与输入。

**审稿人会问**：这不就是把 Coppelia 的搜索空间约束一下吗？
**回答**：不是。约束改变了问题的性质——从"是否存在触发程序"（SAT 问题）变成"给定程序是否存在触发路径"（受限的路径存在性问题）。而且它引入了**操作数可控性**这一新维度：片段存在不等于操作数可控于外部输入。

### 创新点 B：硬件触发语义到固件片段的跨层语义匹配

**问题**：硬件侧反推的是架构级语义，固件是编译器产物，两者形式不匹配。
**贡献**：IR 层的语义匹配方法 + 编译器优化等价性规则。

这个点相对工程化，但很实际，适合做专利。

### 创新点 C：约束进展度作为跨层搜索反馈

**问题**：覆盖率与"能否触发硬件漏洞"弱相关。
**贡献**：用 HW-SCM 前提的谓词满足度作为适应度。

这个点适合作为 A 的补充，单独发可能份量不够。

**我的建议**：**A 作为主创新点，B 和 C 作为支撑**。专利可以基于 B 单独申请（因为 B 更具体、更容易写成权利要求）。

## 8. 我对这个方案的风险评估（诚实版）

**最大的单点风险**：Microscope 的二进制版可能不好用，或者输出格式不适合我的流程。
→ **缓解**：第 1 周就必须验证。如果不行，退化方案是**人工从 HardFails 的 5 类 bug + 25 条安全性质中构造触发契约**（HardFails 论文给了安全性质，这是很好的替代来源），论文改成"人工契约 → 自动固件匹配"，创新点变弱但不致命。

**第二大风险**：KLEE 装不上 / 符号执行在固件上路径爆炸。
→ **缓解**：angr 替代；路径爆炸用"从实际轨迹出发的局部求解"（FuSS 的思路）缓解。

**第三大风险**：导师认为这个范围太窄、不算完成第五部分。
→ **缓解**：主动沟通，把它定位成"第五部分的**技术内核**"，其余部分（平台、样本库、多架构）由团队其他成员或后续工作补齐。同时把 CLEG 数据模型设计成能容纳完整的第五部分需求（我在 `schemas/` 里已经这么做了）。

**诚实的结论**：这个方案能产出**一篇像样的会议/期刊论文 + 1-2 项专利**，但不能独立完成项目书第五部分的全部验收指标。**这个边界我会在第一次汇报时就说清楚。**
