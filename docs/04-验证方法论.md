# 跨层漏洞分析器 —— 验证方法论

本文件记录**为什么**这套测试是这样设计的。它比测试代码本身更重要：
测试代码回答"跑没跑通"，本文件回答"跑通了能说明什么"。

---

## 一、核心难点：没有可用的真值

跨层漏洞分析器的验证有一个根本困难：

> **没有人知道答案。**

如果有一份固件，没人能事先说清"它到底能不能触发这个硬件漏洞" ——
如果能说清，这工具就没有存在价值了。所以无法用"和人工标注对比"
来评估，也无法用现成的数据集。

这逼迫我们必须**自己造真值**，而自造真值有它自身的陷阱。

---

## 二、三层真值构造（从下往上，逐层建立可信度）

### 第 1 层：指令编码真值 —— `test_encoder.py`

我们手写 RISC-V 编码器来生成样本。**但手写的编码器本身可能是错的。**
如果编码器和分析器有同样的误解（比如都把 `jr t0` 的 t0 当链接寄存器），
测试就会一起错，然后一致地通过 —— 这是**自洽的错误**。

对策：用 **capstone 独立交叉验证**编码器。capstone 是第三方实现，
它的正确性不依赖我们对 RISC-V 的理解。

交叉验证必须处理伪指令展开，否则会误报：

| 我们写的 | capstone 反汇编成 | 说明 |
|---|---|---|
| `nop` | `addi x0, x0, 0` | 伪指令展开 |
| `ret` | `jalr x0, ra, 0` | 伪指令展开 |
| `mv rd, rs` | `addi rd, rs, 0` | 伪指令展开 |
| `j off` | `jal x0, off` | 伪指令展开 |
| `jr rs` | `jalr x0, rs, 0` | ★ 展开后**只有一个寄存器**，但语义是跳转目标 |
| `csrr rd, csr` | `csrrs rd, csr, x0` | 伪指令展开 |

还要比较**立即数的数值**而非字符串（`0x18` vs `24`），
以及解析内存操作数的 `base`/`disp` 结构。

**结果：59/59 通过。** 这一层立住了，上面两层才有意义。

### 第 2 层：IR 提升真值 —— `test_lifter.py`

反汇编 → 统一 IR。核心断言是**操作数角色不要搞错**：

- STORE 的所有操作数都是源（含地址基址），无目标
- BRANCH 的最后一个立即数是**跳转偏移**，不是比较值
- LOAD 的 MEM 操作数是源（地址），`rd` 才是目标
- `jalr` 的操作数个数随助记符而变（见上表）

其中"BRANCH 的立即数不是比较值"曾经是一个真实 bug：
把跳转偏移当成比较对象，会让所有条件分支的可控性判定失真。

### 第 3 层：端到端判定真值 —— `run_all.py`

手工设计**语义上明确**的固件样本，每个样本考一个具体能力。
关键是：样本的脚本要短到**人能一眼看出正确答案**。

例如 S11（污点清除）：

```
lw   a1, 0(a0)     ; a1 = 输入（污染）
li   a1, 64        ; a1 被常量覆盖 → 污染失效
li   a2, 8
divu a4, a1, a2    ; 两个操作数最终都是常量
ret
```

任何人都能判断：这不可利用。如果分析器说"可控"，就是**假阳性**。

## 三、样本设计原则

### 原则 1：每个样本考**一个**能力，且名字说清考什么

样本名不是"test01"，而是 `S6_neg_folded_chain`。
看名字就知道它在测多级常量折叠。

### 原则 2：必须包含对抗性样本，而不是"能跑就算过"

全部 13 个样本里，有 5 个是专门设计来**打穿幼稚实现**的：

| 样本 | 打穿的幼稚实现 |
|---|---|
| `S6_neg_folded_chain` | "只查操作数是不是寄存器" → 多级折叠后仍是常量 |
| `S8_neg_load_derived` | "非常量即可控" → 常量地址 load 的值未知但不可控 |
| `S10_neg_dead_after_ret` | "块存在即考虑" → `ret` 之后是死代码 |
| `S11_neg_taint_killed` | "污点只累加不清除" → 被后续常量赋值覆盖 |
| `S12/S13_indirect_*` | "间接跳转丢弃即可" → **制造假阴性** |

### 原则 3：区分"判定方向"与"判定精度"

`not_controllable` 比 `present_but_uncontrollable` 更精确，
但两者都表示"不可利用"。若直接比较字符串，会把更精确的判定算成失败。

对策：**语义分组**。

```python
VERDICT_GROUPS = {
    "exploitable_candidate":       "EXPLOITABLE",
    "path_dependent":              "PARTIAL",
    "unknown":                     "UNKNOWN",
    "not_controllable":            "UNEXPLOITABLE",
    "present_but_uncontrollable":  "UNEXPLOITABLE",
    "present_but_unreachable":     "UNREACHABLE",
    "not_present":                 "ABSENT",
}
```

评分比 `got_groups & expected_groups`，不比字面。

### 原则 4：★ `binary_label` —— 不要把"考查别的性质"的样本算进准确率

**这是本项目踩过的一个真实坑。**

S12/S13 的 `expected_verdicts` 列了多个可接受判定（含
`exploitable_candidate`），因为它们考查的是"**不得误报不可达**"，
而不是"它一定可利用"。结果它们被当成"正样本"计入 Precision/Recall，
产生了一个**根本不存在的 FN=2**，把 Recall 从 100% 拉到 66.7%。

这种"看起来像漏报，其实是评分口径错了"的错误很危险 ——
它会让作者去修一个不存在的问题，或者反过来掩盖真问题。

对策：`Sample.binary_label` 显式标注：

| 取值 | 含义 |
|---|---|
| `exploitable` | 正样本，计入 TP/FP/FN |
| `unexploitable` | 负样本，计入 TN/FP/FN |
| `excluded` | 只计入逐样本正确性，**不计入二分类指标** |

报告中必须打印被排除的样本数，不能静默排除。

## 四、为什么最终的指标是 Precision/Recall 而不是"准确率"

对安全工具而言，两类错误代价**不对称**：

- **假阳性**（把不可利用报成可利用）：浪费人工，可能被当成误报工具弃用
- **假阴性**（把可利用报成不可利用）：**说安全，其实不安全**

假阴性更危险。所以必须**分开报告**，不能用一个"准确率"掩盖：
一个把 100 个样本全判"安全"的工具，在 95% 负样本的数据集上准确率 95%，
但它毫无价值。

当前结果：

```
TP=4  FP=0  TN=7  FN=0
Precision = 100.0%   Recall = 100.0%
未计入二分类 2 个（考考查可达性保真）
```

**FP=0 是最重要的数字。**

## 五、证据图不变量检查 —— `test_evidence.py`

`evidence.py` 的 docstring 承诺了三件事：

1. 推理边与观测边严格分离
2. 每条边带可求解条件
3. 边可被反事实反驳

**如果这些承诺不被机器检验，它们就只是文档措辞。**

本测试把每条承诺变成断言：

| 编号 | 不变量 |
|---|---|
| I1 | 节点类型在白名单内 |
| I2 | `edge_nature` ∈ {inference, observation}；`edge_type` 合法 |
| I3 | **推理边的证据级别必须 ≤ E1** |
| I4 | **观测边的证据级别必须 ≥ E2** |
| I5 | 观测边必须携带仪器/来源（禁止凭空断言"我观测到了"） |
| I6 | `triggers` 边必须带 `condition.satisfiability` |
| I7 | `triggers` 边必须带 `condition.unsatisfied_predicates` |
| I8 | `equivalent_to` 边必须带语义等价依据 |
| I9 | `counterfactual_tested=true` 必须带 `counterfactual_result` |
| I10 | 统计量自洽：inference + observation == edges |
| I11 | 内容寻址存储：同内容同 hash，只落一份 |
| I12 | 反驳记录可写可读 |

### ★ 元测试：检查器本身必须被检查

一个永远返回"通过"的检查器守护不了任何东西。
所以 `test_negative_cases_are_detected` 故意往图里塞**写错的边**，
断言这些错误**必须被检出**：

- 推理边标 E4 → 必须报 I3
- 观测边标 E0 → 必须报 I4
- 观测边无来源 → 必须报 I5
- `triggers` 边无 condition → 必须报 I6
- 非法 `edge_nature` → 必须报 I2

**这个测试当场抓到了一个真实的设计自相矛盾**：
我把 `located_in` 边标成 `inference` + `E4`。
E4 意味着"已在物理板卡上验证"，但那是推理边 —— 等于把推断伪装成观测。
修复：边记为 E1，把"镜像 sha256 是 E4 级事实"放进
`firmware_identity_evidence_level` 字段（事实字段，不改变边的性质）。

## 六、控制流可信度的自证

间接跳转解析采用过近似后，必须回答一个问题：

> 我怎么知道过近似**真的生效了**？

对策：把解析情况变成**可观测的指标**，并写进报告：

```
indirect_jumps        = 1    间接跳转总数
indirect_resolved     = 1    已解析出目标
indirect_unresolved   = 0    走兜底
cfg_confidence        = medium
```

诊断脚本 `_diag_indirect.py`（开发期工具）直接打印每个块的可达性与后继，
用来确认"目标块从 reach=False 变成 reach=True"。

以 S12 为例，修复前后的对比是可验证的：

| | 修复前 | 修复后 |
|---|---|---|
| `0x80000018`（触发点） | `reach=False` | **`reach=True`** |
| `indirect_resolved` | 0 | **1** |
| `unreachable_blocks` | 3 | 2（只剩真的死代码） |

**注意这里的关键**：修复后仍有两个块被判不可达（`0x80000010`、`0x80000014`
的两个 `ret`）—— 这正说明解析是**精确**的，不是无脑把所有块都接上。

## 七、反向验证：如何确认没在骗自己

最后，一套自检清单，每次改动后逐条过一遍：

- [ ] 语法全量扫描 0 错误（`py_compile` 遍历所有 `.py`）
- [ ] 编码器 vs capstone：59/59
- [ ] 证据图不变量：全通过（含负例元测试）
- [ ] 端到端：13/13，**FP=0**
- [ ] 被排除出二分类的样本数被显式打印
- [ ] 新增的每个样本都有 `binary_label`
- [ ] 若新增了"过近似"逻辑，必须同时新增 `*_resolved` 一类指标
- [ ] 报告中每一句"未进行/未建模"的声明都真实

**最后一条最重要**：报告里凡说"未验证"的地方，必须真的未验证；
凡说"已实现"的地方，必须真的能跑。这套工程的诚实性靠这条守住。
